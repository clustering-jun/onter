# 온터 웹 플랫폼 설계

2026-11-18 현재 상태. 알고리즘 쪽 설계는 `project/model/docs/00_system_architecture.md`, 바꿔 온 과정은 `02_변경기록.md`.

## 1. 구조

```
브라우저(web/)                          서버(server/)                           자료·모델
┌───────────────┐  JSON   ┌────────────────────────────┐
│ index.html     │◀──────▶│ app.py  라우터·정적 파일      │
│ js/core.js     │         │  ├ engine.py   순위·묶음·상태  │◀── project/model/onter (m1~m4, explain)
│ js/main.js     │         │  ├ catalog.py  조회용 자료     │◀── project/data/processed
│ js/tabs/*.js   │         │  ├ llm_service 문장·점검표     │◀── Ollama(로컬)
│ css/app.css    │         │  ├ store.py    사용자 입력     │──▶ data/user_state.json
│ Leaflet·글꼴(CDN)│        │  └ /kg/*  Knowledge Graph     │◀── project/knowledge_graph
└───────────────┘         └────────────────────────────┘
```

- **서버**: 파이썬 표준 라이브러리 `ThreadingHTTPServer`. 이 PC는 pydantic 버전이 충돌해 FastAPI를 쓸 수 없고, 추가 설치 없이 돌게 하려고 골랐다. HTTP/1.1 연결 유지, IPv6 루프백 수신, 연결 대기열 128.
- **계산은 일꾼 스레드 하나에서**: 요청마다 생기는 스레드에서 pandas·numpy를 돌리면 Windows에서 프로세스가 접근 위반(0xC0000005)으로 죽었다. 그래서 모든 계산을 `engine.run()`으로 보내 스레드 하나에서 차례로 처리한다. 요청 스레드는 입출력과 LLM 호출만 맡는다. **새 API를 만들 때도 pandas·numpy를 쓰는 부분은 `engine.run()` 안에 둔다.**
- **엔진**: 시작할 때 한 번(약 5초) 단지×프로그램 행렬, 이웃 유사도, 근거 성분 점수, 필요 지수, 요건, 여건을 메모리에 올린다. 요청마다 단지 한 곳의 96개 프로그램 벡터만 다시 계산한다(순위 약 2ms, 정수계획 약 4ms). 기본값의 결과는 오프라인 산출물과 318개 단지 모두 같다.
- **화면**: 빌드 없는 ES 모듈. 탭마다 파일 하나(`js/tabs/`). 그림은 직접 그린 SVG와 CSS 막대.

## 2. 화면 배치의 원칙

| 원칙 | 적용 |
|---|---|
| 전체 화면을 쓰는 탭은 스크롤하지 않는다 | 지도, 프로그램 추천, Knowledge Graph는 화면 높이에 맞춘 칸으로 나누고 칸 안에서만 스크롤 |
| 읽는 탭은 폭을 제한한다 | 나머지 탭은 본문 최대 1500px, 가운데 정렬 |
| 긴 화면에는 목차 | 상자 제목(h3)이나 `data-toc`으로 만든 목차가 탭 아래에 고정되고, 보고 있는 위치를 표시(`core.buildToc`) |
| 머리는 항상 보인다 | 탭 메뉴는 스크롤해도 위에 고정. 높이는 `--topH` 변수로 나눠 쓴다 |
| 창 크기에 따라 변한다 | 글자 크기는 모두 rem, 기준 크기는 창 너비에 따라 12~16px. 좌우 칸 폭과 여백도 창 너비에 비례 |
| 점수는 감춘다 | 순위 숫자에 마우스를 올려야 점수가 보인다 |
| 값은 상대 위치와 함께 | "318곳 중 상위 5%", 평균과의 차이, 순위 |
| 비어 있는 값과 0을 섞지 않는다 | 3절 |

## 3. 상태 구분

| 표시 | 뜻 | 정하는 곳 |
|---|---|---|
| 자료 없음(기울임) | 결측. 거리·만족도·추세 등 값이 비어 있음 | 서버가 `null`로 보내고 화면이 표시 |
| 기록 없음 | 단지의 활동 기록 자체가 없음(12곳) | 엔진 `has_rec` |
| 미운영 | 단지에 기록은 있는데 이 프로그램 기록은 없음 | 30개월 기록 |
| 운영 중 | 최근 12개월 안에 기록 있음 | 〃 |
| 과거 운영 | 기록은 있지만 최근 12개월에는 없음. 재개 검토 대상 | 〃 |
| 운영 불가능 | 사용자가 표시 | `store.py` |
| 보류 | 사용자가 '지금은 아님'으로 뺌 | 〃 |
| 운영 중(기록 누락) | 사용자가 이미 하고 있다고 표시 | 〃 |

해피콜 만족도도 같은 원칙이다: 연결된 관리소 없음 / 통합 관리소 값이라 단지 값으로 보지 않음 / 응답 30명 미만 / 복지 문항 응답 없음을 따로 표시한다.

## 4. 후보가 모자랄 때

1. 새 후보(미운영·기록 없음이면서 제외하지 않은 것)를 먼저 넣는다.
2. 모자라면 과거 운영 프로그램을 '재개 검토' 표지와 함께 넣는다.
3. 그래도 모자라면 '지금은 아님'으로 뺀 프로그램 가운데 뺀 횟수가 2번 이하인 것을 '다시 제안' 표지와 함께 넣는다.
4. 운영 불가능, 이미 운영 중, 3번 넘게 뺀 프로그램은 넣지 않는다. 요청 수보다 적게 나올 수 있다.

## 5. 확인된 필요

- 단지 현황에서 분야별로 낮음(0.1)·보통(0.5)·높음(0.9)을 고르면 그 분야의 필요 백분위 자리에 이 값을 넣어 필요 적합과 목표 분포를 다시 계산한다.
- '높음'으로 확인한 분야에서는 점수순 상위 2개를 목록에 먼저 넣는다.

## 6. LLM

화면에 들어가면 자동으로 만든다. 요청 버튼은 없다.

| 쓰임 | 언제 | 검사 | 떨어지면 |
|---|---|---|---|
| 추천 근거 문장 | 후보를 고를 때 | 숫자·단정 표현, 형식, 숫자가 제 뜻에 붙어 있는지 | 규칙 문장 |
| 실행 점검표 | 점검표 탭을 열 때 | JSON 형식, 묶음 5개·항목 수, 사실에 없는 숫자, 단정·기간·해석 표현, 미배치 단지에서 주거복지사가 하는 일로 쓴 항목 | 규칙으로 만든 점검표 |
| 묶음 설명 | 묶음이 정해지고 0.9초 뒤 | 숫자, 단정·해석 표현, 사실에 없는 주거복지사 언급, 인력 단위, 프로그램 이름을 바꿔 쓴 경우, 5문장 이내 | 규칙 문장 |

- 배치로 미리 만든 근거 문장(`project/model/outputs/llm/explanations_llm.jsonl`)은 사실이 같을 때 바로 쓴다.
- 결과는 사실 목록의 해시로 `data/llm_cache.json`에 둔다.
- 한계: 검사는 숫자와 정해 둔 표현을 본다. 숫자가 아닌 지어낸 내용이나 틀린 집계(분야별 개수 등)는 통과할 수 있다.

## 8. Knowledge Graph 붙이기

`project/knowledge_graph`의 파일은 고치지 않는다.

- 서버가 그쪽 `server.py`를 모듈로 불러 `/kg/api/*` 요청을 그 핸들러에 넘긴다.
- `/kg/` 파일을 내보낼 때 바꾸는 것(`app.py`): API 주소(`/api/` → `/kg/api/`), 초록·베이지 색(→ 청록·회색, `_kg_recolor`), 작은 글씨(→ 14px 이상, `_kg_bigger`), 글꼴과 덮어쓰기 스타일(`css/kg_embed.css`).
- API 응답에서 사례·사례 카드의 긴 제목을 "이름 (지역) — 설명 앞부분"으로 줄인다(`_kg_short`).
- 탭에서는 iframe으로 열고 `#focus=complex:단지ID` 또는 `#focus=program:프로그램ID`로 바로 들어간다.
- 그래프는 만든 시점의 스냅샷이다. 추천 후보와 설명은 플랫폼의 추천 화면이 최신이다.

## 9. API

| 방식·경로 | 인자 | 응답 |
|---|---|---|
| GET `/api/meta` | - | 분야·유형·상태 이름, 유형 설명, 기본값, 개수, 사진이 있는 단지 |
| GET `/api/complexes` | - | 지도용 단지 목록 |
| GET `/api/complex` | id | 단지 카드와 현황 전체 |
| GET `/api/matrix` | id | 프로그램 96종의 상태표 |
| GET `/api/recommend` | id, w, lam, k, domain | 후보 목록(감춘 점수 포함), 부족 안내, 분야별 상위 3개, 목록·목표 분포, 계산 시간 |
| GET `/api/candidate` | id, sid | 근거, 사례, 걸림돌, 점검표(규칙), 요건 |
| POST `/api/plan` | id, w, lam, budget, hours, n_max, min_domains | 묶음, 합계, 달력, 풀이 시간 |
| GET `/api/programs`, `/api/program` | sid | 프로그램 목록·상세 |
| GET `/api/search` | q | 프로그램·단지·사례·소식 |
| GET `/api/cases`, `/api/happycall`, `/api/analytics` | - | 조회용 자료 |
| GET `/api/state`, POST `/api/state/confirm·exclude·restore·memo` | id, … | 사용자 입력 |
| GET `/api/llm/status`, POST `/api/llm/explain·checklist·plan` | id, sid, … | LLM 결과와 출처 |

오류는 `{error}`와 함께 404(없는 단지·프로그램), 400(잘못된 값), 500으로 돌려준다.

## 10. 검증한 것과 못 한 것

- `tests/test_api.py`: 31항목(LLM 포함 35항목) 통과.
- 서버 안정성: 요청 1,950건을 차례로, 60묶음을 동시에 보냈을 때 죽지 않음. 동시 60묶음에서는 9건의 연결이 끊겼고, 대기열을 늘린 뒤에는 다시 재지 않았다.
- CSS 정리 뒤 10개 화면의 모든 요소에서 글자·여백·색 등 17개 속성이 정리 전과 같음을 확인(창 너비 1600px).
- 못 한 것: 인터넷이 끊긴 상태의 지도 탭, 여러 사람이 동시에 저장할 때의 충돌(파일 잠금만 있음), 좁은 창에서의 CSS 정리 전후 비교, 실제 사용자 평가.
