# LLM 활용 계획과 실행 결과

현재 상태(2026-11-18): 로컬 LLM으로 근거 문장 다듬기를 구현하고 추천 3,180건 전체를 돌렸다. 외부 API는 쓰지 않는다.

- 서버: Ollama 0.40.16, 모델 `exaone3.5:7.8b`, RTX 5090. `serve_ollama.ps1`이 병렬 슬롯 8로 다시 띄운다.
- 연결: `onter/llm.py`의 `ollama_fn()`이 `explain(rec, llm_fn=...)`에 넣을 함수를 만든다. Python SDK `ollama`를 쓰고, SDK를 불러올 수 없으면 HTTP(`/api/chat`)로 직접 부른다. 2026-11-18 현재 이 PC는 pydantic과 pydantic-core 버전이 맞지 않아 SDK가 불러와지지 않으므로 HTTP 경로로 돌았다.
- 배치: `run_llm_explain.py`. 결과 `outputs/llm/explanations_llm.jsonl`, 요약 `results/llm_explain_summary.json`.

## 쓸 곳과 쓰지 않을 곳

| 쓰임 | 판단 | 이유 |
|---|---|---|
| 근거 문장 다듬기 | 구현함 | 템플릿 문장이 딱딱하다. 입력은 근거 사전뿐이라 위험이 작다 |
| 사례 카드 요약(단지 맥락에 맞춘 2~3문장) | 쓴다(선택), 미구현 | 사례집 카드가 길다 |
| 새 활동 기록의 표준 프로그램 분류(검색 3순위 안에서 고르기) | 검토, 미구현 | 검색 첫 순위 적중 74%, 3순위 90%. 나머지를 LLM이 고르면 입력 부담이 준다 |
| 전문가 시트 B의 빈칸 초안 | 검토 | 사람이 고치는 초안으로만 |
| 순위 점수 계산 | 쓰지 않는다 | 재현되지 않고 근거를 댈 수 없다 |
| 필요 지수 | 쓰지 않는다 | 같은 이유 |

## 실행 설정

| 항목 | 값 | 이유 |
|---|---|---|
| temperature | 0.15 | 없는 숫자를 만들지 않게 |
| num_predict | 220 | 문장이 길어지지 않게, 빨리 끝나게 |
| num_ctx | 2048 | 입력이 짧다. 슬롯 8개를 올려도 메모리가 남는다 |
| 병렬 | 서버 `OLLAMA_NUM_PARALLEL=8`, 배치 `--workers 8` | 두 값을 맞춘다 |
| seed | 20261118 | 다시 돌렸을 때 차이를 줄이려고(병렬 실행이라 완전히 같지는 않다) |
| 재시도 | 1회 | 떨어진 이유를 붙여 다시 시킨다 |

프롬프트는 규칙 5개와 예시 2개(필요 지표가 있는 경우, 없는 경우)를 시스템 메시지에 두고, 사용자 메시지에는 단위를 붙인 한국어 사실 목록만 넣는다(`explain.facts_text`).

## 검사(통과하지 못하면 템플릿 문장을 쓴다)

1. `check_grounded`: 문장의 숫자가 모두 사실 사전에 있고, 단정 표현이 없다.
2. `check_form`: 길이, 한자·가나 없음.
3. `check_binding`: 숫자가 제 뜻에 붙어 있다. %는 '상위 N%'이거나 '전체 단지' 비율이어야 하고, 곳·건·장·만 원·단계·월 앞의 숫자가 각각 맞는 사실이어야 한다. 사실에 없는 해석(최고, 중간 수준, 참여율, 규모 등)이 없고, 필요 지표를 주지 않았는데 필요를 말하지 않고, '후보'라는 말이 있고, 5문장 이내(미배치 경고가 있으면 6문장)다.

3번을 둔 이유: 처음 표본 40건에서 숫자 검사는 97.5%가 통과했지만 읽어 보니 뜻이 바뀐 문장이 있었다. 전체 단지 운영 비율 64%를 "비슷한 단지 20곳 중 약 64%인 12곳"으로 쓰거나, 11·1·2월을 "1월부터 3월"로 쓰거나, "높은 참여율", "비슷한 규모의 단지"처럼 사실에 없는 말을 붙였다. 숫자만 보는 검사로는 이런 문장을 거를 수 없다.

## 결과(추천 3,180건 전체, 전문가 요건 반영 뒤 다시 돌린 최종본)

| 항목 | 값 |
|---|---|
| 걸린 시간 | 36분(분당 88건, 건당 0.68초, 초당 307토큰) |
| 숫자·단정 표현 검사만 본 통과율(1차) | 99.6% |
| 세 검사 모두 통과(1차) | 65.6% |
| 재시도 후 통과 | 93.4% |
| 템플릿 문장으로 대체 | 6.6% |
| 서버 오류 | 0건 |
| 평균 길이 | LLM 278자, 템플릿 230자 |

전문가 요건을 넣기 전 첫 실행(인력 부담 등급 문구)은 13.6분, 1차 통과 84.4%, 재시도 후 85.2%였다. 문구를 '실행 난이도'로 바꾼 뒤 1차 통과가 떨어지고 재시도가 늘어 시간이 길어졌다. 대신 재시도가 잘 듣게 되어 최종 통과율은 올랐다.

떨어진 이유(1차, 건수): '중간 수준' 737(난이도가 3이 아닌데 중간이라고 씀), '통찰' 126, '필요' 101(필요 지표를 주지 않은 추천에서 필요가 높다고 씀), '비교적' 98, 문장 수 초과 50. 난이도 해석은 척도와 맞을 때만 허용한다(1~2 낮음, 3 중간, 4~5 높음).

## 판단

- 속도는 문제가 아니다. 전체를 40분 안에 다시 만들 수 있어 실시간 호출이 필요 없다.
- 숫자 환각은 낮은 temperature와 단위를 붙인 사실 목록으로 거의 없어졌다(0.4%). 남은 위험은 숫자가 아니라 **해석을 덧붙이는 것**이고, 이것은 규칙 목록으로 거른다. 목록에 없는 새 표현은 통과할 수 있다("참고하시면 도움이 될 것입니다" 같은 군말이 남아 있다).
- 통과한 문장 약 25건을 직접 읽었을 때 사실이 바뀐 것은 없었다. 다만 템플릿보다 21% 길고, 내용은 같다. 읽기 좋아졌는지는 현장 직원 평가가 있어야 말할 수 있다.
- 그래서 웹에서는 템플릿 문장을 기본으로 두고, LLM 문장은 검사를 통과한 것만 바꿔 끼우는 선택 사항으로 둔다. `outputs/recommendations_detail.jsonl`의 `explanation`은 템플릿 그대로다.
- **요건이나 순위가 바뀌면 LLM 문장도 다시 만들어야 한다.** `build_outputs.py` 뒤에 `run_llm_explain.py --fresh`를 돌린다.

## 남은 실험

1. 현장 직원 5명 안팎의 읽기 평가(템플릿 대 LLM, 가려서).
2. 통과 문장 표본 100건의 사람 검수로 `check_binding`이 놓치는 비율 추정.
3. 분류 보조: 평가 구간의 처음 보는 제목 3,000건에서 '검색 3순위 + LLM 선택'의 첫 순위 적중률.
4. 병렬 수(4·8·16)와 모델 크기(2.4b)의 속도·통과율 비교: `--workers`, `--model`, `--tag`로 따로 저장해 비교할 수 있다.
